# nfl-game-predictor
Machine learning model to predict NFL game outcomes using Random Forest classification with engineered features from historical data

## Architecture

### How did you structure your machine learning pipeline, and what architectural decisions did you make to ensure scalability and maintainability?
The architecture of this NFL game prediction system was designed with modularity and reproducibility as core principles. Structuring the project into two distinct pipelines: data acquisition and model training, each encapsulated in separate Jupyter notebooks to maintain clear separation of concerns. The data collection pipeline (NFLWebScraping.ipynb) implements a robust web scraping framework that handles rate limiting, error recovery, and data validation. This ensures that any failures during scraping don't corrupt the entire dataset.The model training pipeline (NFLGamePredictor.ipynb) follows a temporal structure that mirrors real-world deployment scenarios. Rather than using random train-test splits, which would introduce data leakage, implementing a strict temporal split where all training data precedes all testing data. This architectural choice was critical because it prevents the model from "seeing the future" during training which is a common pitfall in time-series prediction tasks. The feature engineering component uses a sliding window approach with closed='left' parameter in pandas rolling calculations, ensuring that rolling averages for game N only incorporate information from games N-3, N-2, and N-1. This temporal integrity in the architecture ensures that model performance metrics accurately reflect what would be achievable in production.

## Functionality

### Walk me through the core functionality of your prediction model. How does it process raw data into predictions, and what makes your feature engineering approach effective?
The core functionality centers on transforming raw game statistics into predictive features that capture team momentum and relative strength. When the system processes a game prediction, it first retrieves the target team's rolling averages over their previous three games—metrics like yards per play, third-down conversion rate, time of possession, points scored, and turnovers. Simultaneously, it retrieves the opponent's rolling statistics from their last three games. This dual perspective is crucial because it doesn't just ask "how good is Team A?" but rather "how does Team A's recent offensive performance compare to Team B's recent defensive performance, and vice versa?" The model then evaluates these 28 engineered features through a Random Forest classifier with 150 decision trees, each providing a vote on the predicted outcome.
The feature engineering approach is grounded in the principle that recent performance is more predictive than season-long averages in the NFL, where momentum, injuries, and team evolution play significant roles. The three-game rolling window strikes a balance between capturing current form without overreacting to single-game anomalies. For example, if a team's quarterback gets injured in week 7, their rolling averages for weeks 8-10 will reflect this change, making predictions more contextually accurate than using season-to-date statistics that would dilute this critical information.

## Testing

### How did you validate your model's performance, and what testing strategies did you implement to ensure the predictions are reliable and not overfitted?
Model validation in this project required careful attention to temporal integrity and realistic performance assessment. I implemented a strict temporal holdout strategy where the model trains exclusively on seasons 2002-2012 and tests on the 2013-2014 seasons. This 11-year training period provides 5,632 games for the model to learn patterns, while the 2-year test period with 1,024 games offers sufficient data to assess generalization performance. This approach is fundamentally different from random cross-validation because it simulates real-world deployment where the model would be predicting future games it has never seen. Random splitting would artificially inflate performance metrics by allowing the model to learn from games temporally adjacent to test cases, creating an unrealistic evaluation scenario.
I evaluated the model using multiple complementary metrics to gain a comprehensive understanding of its strengths and weaknesses. Precision score (59.27%) measures how often the model is correct when it predicts a win, which is crucial for understanding prediction reliability. Accuracy (56.86%) provides overall correctness across all predictions. An interesting validation finding emerged when I filtered for "high-confidence predictions"—games where the model predicted one team to win and explicitly predicted the opponent to lose. In these 284 decisive predictions, accuracy jumped to 63.23%, suggesting the model is more reliable when the feature patterns strongly favor one team. This meta-analysis of prediction confidence provides valuable insight: in production, a user might weight high-confidence predictions more heavily than close calls.
To guard against data leakage, I implemented several testing safeguards. First, the rolling average calculations use closed='left' in pandas, explicitly excluding the current game from its own rolling statistics. Second, I ensured that the opponent's rolling statistics used in predictions come from their previous games, not from the game being predicted. This is non-trivial because both teams appear in the same dataset row, but I validated that Arizona's prediction against Seattle uses Seattle's pre-game rolling averages, not statistics from the Arizona-Seattle game itself. Third, I verified temporal ordering by confirming no test set games have dates earlier than any training set games. These validation steps are tedious but essential—data leakage is one of the most common pitfalls in machine learning projects, and temporal data requires extra vigilance. The model's 57-59% performance range reflects true predictive capability rather than inflated metrics from leakage, giving confidence that these results would translate to production deployment.


## Reflection

### Looking back on this project, what were the key challenges you faced, what would you do differently, and how does this work demonstrate your growth as a data scientist?
This project crystallized several important lessons about the realities of applied machine learning. The most significant challenge was confronting the gap between theoretical model performance and the inherent unpredictability of NFL games. Initially, I expected higher accuracy—perhaps 70-75%—given the wealth of statistical data available. Achieving only 57-59% accuracy was initially disappointing until I researched that even sophisticated Vegas betting models, which incorporate far more information (injury reports, weather, betting line movements, advanced metrics), typically achieve 52-55% accuracy against the spread. This contextualization was humbling: my model, using only basic box score statistics, actually performs comparably to professional systems when accounting for the information available. The lesson here is that model performance must be evaluated against domain-specific baselines, not absolute expectations, and that some problems have fundamental complexity bounds that data and algorithms alone cannot overcome.
If I were to rebuild this project, I would make several architectural and methodological improvements. First, I would incorporate hierarchical modeling to capture the fact that teams improve or decline within seasons—a linear trend component added to rolling averages might better capture teams "getting hot" versus merely performing well in isolated games. Second, I would implement proper hyperparameter tuning using time-series cross-validation rather than using default Random Forest parameters. My current approach uses n_estimators=150 and min_samples_split=10 based on initial experimentation, but a systematic grid search over hyperparameter space with proper temporal folds would likely yield better performance and provide insight into model sensitivity. Third, I would build a more sophisticated feature engineering pipeline using domain knowledge from NFL analytics—metrics like "strength of schedule" (quality of recent opponents), "yards per play differential" (always among the strongest predictors in football analytics), and "turnover luck" (turnovers are somewhat random and may regress to the mean). Finally, I would implement ensemble methods, combining Random Forest with gradient boosting and logistic regression, as diverse models often capture complementary patterns.
This project represents significant growth in my understanding of the full machine learning lifecycle. Prior projects I completed used pre-cleaned datasets from repositories like Kaggle, which obscured the substantial work required in data acquisition and preparation. Building the web scraping infrastructure taught me that data collection is often 60-70% of the work in real projects—handling edge cases, validating data quality, managing rate limits, and designing robust schemas. The temporal validation aspect deepened my understanding that evaluation strategies must match deployment realities; using inappropriate validation (like random splits on time-series data) produces meaningless metrics. Perhaps most importantly, the project taught me to think critically about model limitations and set appropriate expectations. A 57% precision model isn't a failure—it's a meaningful achievement in a complex, high-variance domain. Understanding when "good enough" is actually good, and when to invest in improvements versus accepting fundamental problem complexity, is a crucial skill for production data science. Moving forward, I'm better equipped to scope projects realistically, communicate results in business context, and make principled decisions about the trade-offs between model sophistication and practical value.
